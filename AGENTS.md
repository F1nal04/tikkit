## What this is

Tikkit is a self-hosted IT ticketing system (one organization per deployment) with a requester portal, a shared help-desk queue, team-based support, admin, and optional BYOK AI assistance. The code is early: a landing page plus the API foundation (validated config, PostgreSQL schema/migrations, health/readiness probes); the agreed product requirements live in `spec.md` and implementation is tracked in GitHub issues (roadmap: F1nal04/tikkit#2). **Read `spec.md` before implementing any feature — it is the source of truth for behavior.**

## Commands

Requires Bun ≥ 1.4.3, Node ≥ 22.12, Rust ≥ 1.85 (with rustfmt + clippy). Run from the repo root; Turbo fans out to `apps/*`.

```sh
bun install
docker compose -f compose.dev.yml up -d   # PostgreSQL 16 on 127.0.0.1:5432 (needed by dev and tests)
bun run dev                          # web on :3000, API on 127.0.0.1:3001
bun run dev --filter=@tikkit/web     # or --filter=@tikkit/api
bun run check                        # tsc --noEmit, cargo fmt --check, cargo clippy -D warnings
bun run build                        # vite build (Nitro) + cargo build --release
bun run test                         # web (Vitest) + API (cargo test incl. PostgreSQL integration tests)
bun run test:e2e                     # Playwright browser tests; needs PostgreSQL (see below)
bun run start                        # run production builds (build first)
```

Rust directly (Cargo workspace root is the repo root):

```sh
cargo test -p tikkit-api                              # all API tests
cargo test -p tikkit-api health_returns_json_status   # single test by name
cargo clippy --locked --all-targets -- -D warnings     # must be warning-free; CI fails otherwise
cargo fmt --all
cargo run --locked -- migrate                          # apply migrations and exit
cargo run --locked -- check-config                     # validate env config, print redacted summary
```

Web tests (from `apps/web`, or prefix with `bun run --cwd apps/web`):

```sh
bun run test                                  # Vitest + Testing Library (jsdom), src/**/*.test.tsx
bun run test -- src/components/LandingPage    # single file
bun run test:watch
bun run test:e2e                              # Playwright, e2e/*.spec.ts
bun run test:e2e -- --grep smoke --headed     # filter / watch the browser
```

- Component tests use `vitest.config.ts`, which loads only the React plugin (not TanStack Start/Nitro). Render presentational components directly (keep route files thin, e.g. `routes/index.tsx` → `components/LandingPage.tsx`) and stub `fetch` with `vi.stubGlobal`.
- `test:e2e` starts the Rust API (`cargo run --locked`) and the web dev server itself, reusing ones already running on :3001/:3000 unless `CI` is set. Each run creates a disposable database `tikkit_e2e_<timestamp>_<random>` on `E2E_DATABASE_URL` (default `postgres://tikkit:tikkit@127.0.0.1:5432/postgres`), passes it to the API as `DATABASE_URL`, and drops it in global teardown; leftovers older than 6h from crashed runs are swept on the next run. Playwright starts `webServer` before `globalSetup`, so creation happens in the API server command (`e2e/support/create-database.ts`). Failures keep a trace and screenshot in `apps/web/test-results/`; the HTML report goes to `apps/web/playwright-report/`. Browser tests never need an AI key.
- `@playwright/test` is pinned to an exact version; install browsers with `bunx playwright install chromium` (CI: `--with-deps`). `PW_CHROMIUM_PATH` overrides the Chromium executable.

API contract (see `docs/api.md`): after changing endpoints or DTOs, regenerate and commit both files; CI-equivalent checks (`cargo test`, web `check`) fail on drift.

```sh
UPDATE_OPENAPI=1 cargo test --locked -p tikkit-api openapi   # rewrite apps/api/openapi.json
bun run --cwd apps/web generate:api                          # rewrite apps/web/src/api/schema.gen.ts
```

Notes:

- Always use `--locked` with Cargo (the package.json scripts do); don't let Cargo rewrite `Cargo.lock` silently.
- `@tikkit/web#check` depends on `build` because `src/routeTree.gen.ts` is generated by the TanStack Start Vite plugin. Don't hand-edit that file; it regenerates on dev/build. Likewise never hand-edit `apps/api/openapi.json` or `apps/web/src/api/schema.gen.ts`.
- API handlers return `Result<T, ApiError>` and use the `ApiJson`/`ValidJson`/`ApiPath`/`ApiQuery` extractors; `http::apply_api_layers` must wrap the final router. Frontend code calls the API only through `apps/web/src/api/client.ts`.
- The dev server does not hot-reload Rust. Restart `bun run dev` (or just the api filter) after backend changes.
- Configuration is env-only and validated in `apps/api/src/config.rs` (all vars documented in `docs/configuration.md`). In development (`TIKKIT_ENV` unset/`development`) with `DATABASE_URL` unset the API uses `postgres://tikkit:tikkit@127.0.0.1:5432/tikkit`; production requires `DATABASE_URL`, https `PUBLIC_ORIGIN` and `TIKKIT_ENCRYPTION_KEY`. Turbo runs tasks in strict env mode: new API env vars must be added to the `passThroughEnv` lists in `turbo.json`.
- Integration tests live in `apps/api/tests/` and use `tests/common/mod.rs`: `TestDb::new()` creates and migrates a disposable database on `TEST_DATABASE_URL` (default `postgres://tikkit:tikkit@127.0.0.1:5432/postgres`) and drops it on drop; fixtures cover all five roles and first setup. Tests fail (not skip) without PostgreSQL.

## Architecture

Bun + Turborepo monorepo, two apps, same-origin routing by path prefix:

- `apps/web` — TanStack Start (React 19, file-based routes in `src/routes/`, Vite 8, Nitro for the production server). In dev, Vite proxies `/api` → `http://127.0.0.1:3001` (`vite.config.ts`). The Nitro plugin is only enabled on `build`, deliberately, so the dev proxy runs ahead of Nitro's middleware. Production output: `.output/server/index.mjs`, env `PORT`/`HOST`.
- `apps/api` — Rust crate `tikkit-api` (Axum 0.8, Tokio, serde, sqlx 0.8 on PostgreSQL 16). `lib.rs` exposes `app(AppState) -> Router` (`state.rs`: pool + `Arc<Config>`); `main.rs` parses the CLI (`serve` default, `migrate`, `check-config`), validates config, connects (bounded retry), checks/applies migrations, binds `API_ADDR` and handles graceful shutdown (`server.rs`, SIGTERM/Ctrl+C, drain bounded by `SHUTDOWN_TIMEOUT_SECS`). `db.rs` holds the embedded `MIGRATOR` and the schema compatibility check used by startup and `/api/health/ready`. Keep routes/handlers in the lib so tests can drive the router with `tower::ServiceExt::oneshot` without a socket (see the existing health test). The `package.json` in this dir exists solely to let Turbo invoke Cargo.
- All backend routes are mounted under `/api/*`. In production a reverse proxy sends `/api/*` to Rust and everything else to the Node frontend; changing the API dev port means also changing the Vite proxy.

PostgreSQL is the only database, with one forward-only migration path: `apps/api/migrations/NNNN_name.sql`, embedded via `sqlx::migrate!`, never edited after merge (see `docs/database.md` for schema conventions, e.g. text+CHECK enums and DB-enforced team/lead invariants). Use runtime-checked `sqlx::query`/`query_as` (no compile-time `query!` macros).

Planned per `spec.md` (not yet present): private filesystem volume for screenshots, durable job processing (AI attempts, notification outbox, resolution-confirmation timeouts), Docker Compose deployment. Validation and authorization are enforced in Rust, not the frontend.

## Product invariants that code must preserve

These come from `spec.md` and the implementation issue template (`.github/ISSUE_TEMPLATE/implementation.yml`). Violating them is a bug even if a ticket doesn't mention them.

- **Identity:** accounts are identified by immutable ID and unique normalized username. Email is contact info only; multiple accounts may share an email and must never be merged or compared by it. Ownership and self-handling checks compare account IDs.
- **Self-handling:** the submitting account cannot claim, be assigned, dispatch, reply as staff, note, or resolve its own ticket, regardless of role.
- **Roles/teams:** five roles (User, Operator, Specialist, Team Lead, Admin). Non-admins belong to at most one team; each active team has exactly one lead; Admins cannot be team members or assignees. Protect the last active Admin.
- **Queue/routing:** every human-bound ticket enters one shared general queue with no team or assignee. Dispatch to a team is manual; assignment within a team is manual (claim, or Lead/Admin assign). Never auto-route by category/priority/AI outcome.
- **Team isolation:** after dispatch, staff access is limited to current destination-team members and Admins, everywhere: detail, search, counts, exports, attachments, caches, realtime, queued notifications. On a claimed ticket only the assignee, their Team Lead, or an Admin may write.
- **AI:** disabled by default; one immutable input, one persisted solution per ticket, no chat/regenerate. Only an explicit requester "Solved" marks AI-solved. AI-solved records are final: read-only, never in operator views, never reopenable. Any AI failure must still hand off to humans exactly once. Admin "Skip AI" categories make zero provider calls; requester skip is only allowed if the org toggle is on. Images go to the provider as real image inputs or not at all; never publish private URLs for the provider to fetch.
- **Resolution/closure:** staff-proposed resolution → awaiting requester confirmation; auto-close after Admin-configured timeout (default 168h) with a snapshotted deadline, recorded separately from requester-confirmed closure. Silence never equals acceptance. Rejecting a proposal is not "reopening". Reopening human-closed tickets is behind an Admin toggle, default off.
- **Immutability/audit:** submitted intake is frozen; state transitions are immutable events with provenance; audit events are attributable and never rewritten by normal actions. Secrets (AI keys, SMTP creds) are encrypted, write-only, and redacted from logs/errors/audit.
- **Localization:** English and German everywhere from day one; UTC timestamps; machine identifiers (roles, statuses, errors) stay stable across languages.
- **Scope guard:** no inbound email, no arbitrary file attachments (static PNG/JPEG/WebP screenshots only), no form builder, no multi-tenant, no SLA engine in the first release. Don't build toward deferred scope.

Build authorization, validation, audit events, both languages, and tests alongside each feature rather than deferring them to a "hardening" pass.

## Conventions

- Conventional commits with app scope (`feat(web):`, `fix(api):`). release-please releases `web` and `api` as separate components (`web-vX.Y.Z`, `api-vX.Y.Z`); it attributes commits by touched paths, so keep a commit to one app where possible.
- No `Co-Authored-By` trailers on commits.
