# First-release workflow coverage

Each row follows the order of the acceptance criteria in [issue #48](https://github.com/F1nal04/tikkit/issues/48). Rust tests are under `apps/api/tests/`. The browser tests under `apps/web/e2e/` exercise rendering and client behavior against a stub. The full browser scenarios under `apps/web/e2e-full/` exercise the built portal, real API, and PostgreSQL. The full Playwright scenario runs against the local router or the production Compose stack. It is named “fresh deployment carries human and AI requests through the real portal”. Its named steps identify which part of that workflow a row refers to.

## Product boundaries

- Team edits serialize and preserve exactly one active lead. Replacements of the same team are last write wins between Admins; no stale-write precondition. The test forces two different candidates to contend, checks both 200 responses and the linked audit records, and verifies that the old lead and first replacement remain ordinary members. Two teams competing for the same candidate still have one winner.
- Live ticket access uses activity and queue polling. There is no ticket event stream to test. Row 12 checks loss of access on polls and open pages as well as direct reads and queued delivery.
- The provider mock can verify the instructions, separation of untrusted text and pixels, input minimization, absence of retrieval tools, and fallback when a provider refuses an image. It cannot demonstrate that a real model will follow the instructions. The application has no semantic output filter for a well-formed suggestion that asks for secrets. Row 21 covers the implemented boundary.
- Every selectable first-release model supports images. Invalid or foreign model selection is covered in `selection_is_validated_and_the_connection_status_is_safe`; the browser cannot select an incompatible model. Actual vision failures from the providers are covered in row 25.


## Queue exclusion regression experiment

The local branch temporarily admitted `ai_solved` to the default queue statuses and removed its exclusion from the shared staff SQL predicate. Both changes were needed to simulate an exposed AI-solved ticket because the queue applies both guards. After real submission and explicit requester confirmation, all three provider workflow tests failed on operator queue membership. The existing `ai_stage_and_ai_solved_records_are_absent_from_every_operator_path` failed when the operator general count rose from one to two. The full browser scenario failed at the first operator queue response after solving the English ticket: it returned the AI-solved record instead of an empty queue. Both mutations were restored locally and were never committed or pushed.

## Production Compose verification

`ops/compose/workflows.sh` uses the production API and Node images through Caddy,
fresh PostgreSQL and screenshot volumes, and a test-only Compose overlay. It
runs the full browser scenario without configured SMTP. After baseline human
closure, the official OpenAI HTTPS hostname resolves to a deterministic stub
on an internal bridge. The stock API uses the test CA only in this project.
The browser asserts explicit solve, not-solved handoff, and exactly one
invalid-credential handoff. Adapter-specific Gemini and Anthropic fixtures run
in the real-router integration suite.

The launcher recreates both application containers, verifies their IDs changed,
and keeps the database and screenshot volumes. The browser signs in again
and compares the reference, timeline, explicit closure reason, public messages,
screenshot bytes, AI record and report totals. It checks that the solved record
still stays out of operator detail and queue search. The `compose` job runs the
scenario and uploads browser artifacts on failure.
